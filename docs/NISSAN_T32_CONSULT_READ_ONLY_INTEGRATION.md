# Nissan X-Trail T32 CONSULT Read-Only Integration

## Engineering Design and Validation Guide

**Target vehicle:** Nissan X-Trail T32, 2.5 L gasoline, model year 2015  
**Project:** ESP32 OBD-II client, LILYGO LTE gateway, AWS IoT, and Vehicle Health dashboard  
**Document status:** Design specification — proprietary identifiers must be verified before implementation

> This design intentionally contains no guessed Nissan CAN identifiers, diagnostic addresses, data identifiers, scaling formulas, or security keys. Every proprietary signal must be obtained from an authorized source and validated against the exact vehicle.

## 1. Purpose

The existing firmware reads standard, emissions-related SAE J1979 Mode 01 parameters. This phase extends the platform to selected Nissan-specific diagnostic data for deeper powertrain and vehicle-health analysis while preserving a strictly read-only safety boundary.

The desired result is:

```text
Vehicle ECUs
    |
    | CAN diagnostic requests and responses
    v
ESP32 OBD-II client
    |
    | Private Wi-Fi / TCP / JSON
    v
LILYGO 4G gateway
    |
    | MQTT over TLS
    v
AWS IoT Core -> DynamoDB -> Lambda/API -> Vehicle Health dashboard
```

This is a monitoring system. It is not a scan-tool replacement, ECU programmer, immobilizer tool, or vehicle-control system.

## 2. Vehicle Identity Gate

Do not enable a proprietary decoder until the following identity fields are confirmed:

| Field | Required evidence |
|---|---|
| VIN | Read from the vehicle and recorded outside the public repository |
| Market/region | Thailand, ASEAN, Japan, Europe, or other exact market |
| Engine | Confirm engine code; do not infer it only from displacement |
| Transmission | Confirm CVT/TCM part family and calibration |
| ECU identities | Read ECU part numbers, software versions, and calibration identifiers |
| Network | Confirm 11-bit or 29-bit CAN addressing and diagnostic transport |

Decoder profiles must be selected by verified ECU identity, not only by vehicle model and year. Nissan may change addresses, scaling, availability, and module variants within the same model year.

## 3. Functional Scope

### 3.1 Existing standard OBD-II layer

Retain the current SAE J1979 implementation as the first and most portable layer:

- Engine RPM
- Vehicle speed
- Coolant and intake-air temperature
- Throttle position and calculated engine load
- Fuel trims, oxygen-sensor information, and supported-PID masks
- Control-module voltage and engine runtime
- Read-only diagnostic trouble code reporting

Unsupported PIDs must be displayed as **Not supported**, never as zero.

### 3.2 Proposed Nissan-specific modules

| Module | Candidate read-only information | Priority | Safety condition |
|---|---|---:|---|
| ECM | Nissan-specific engine counters, temperatures, learned values, additional fuel/air data | High | Driving or stationary |
| TCM/CVT | CVT fluid temperature, selected ratio, input/output speed, pressure-related monitor values, CVT DTCs | High | Passive reads; stationary discovery |
| ABS/VDC | Individual wheel speeds, brake-switch status, VDC/ABS DTCs | Medium | Passive reads; no active tests |
| SRS/Airbag | ECU identity and DTCs | Medium | Stationary only |
| BCM | Battery/ignition state, door or body status where legitimately documented | Low | Stationary discovery |
| Combination meter/IPDM | Odometer or power-distribution information where legitimately documented | Low | Stationary discovery |

Signal names in this table are objectives, not proof that a particular ECU exposes them.

## 4. Safety Boundary

### 4.1 Allowed operations

Only the minimum services necessary for observation may be enabled:

- ECU identification
- Read Data by Identifier or equivalent read service
- Read DTC information
- Standard OBD-II Mode 01 and read-only Mode 03/07/0A as supported
- Diagnostic-session entry only when required for documented read access
- Tester-present messages only when required to keep that read session alive

### 4.2 Permanently denied operations

The firmware must reject these operations in production:

- Clear DTC or reset diagnostic information
- ECU reset
- Security access or seed/key exchange
- Write Data by Identifier
- Input/Output Control
- Routine Control
- Request Download, Transfer Data, or Request Upload
- Coding, configuration, adaptation, relearn, and immobilizer operations
- Actuator tests and bidirectional controls
- CAN-frame injection not generated by the allow-listed diagnostic scheduler

Example policy:

```c
bool diagnostic_service_allowed(uint8_t service)
{
    switch (service) {
    case 0x01: /* standard current-data mode, when used by SAE layer */
    case 0x09: /* standard vehicle information */
    case 0x10: /* session control, only for approved read profile */
    case 0x19: /* read DTC information */
    case 0x22: /* read data by identifier */
    case 0x3E: /* tester present */
        return true;
    default:
        return false;
    }
}
```

The actual allow list must be protocol-aware. A numeric service value has meaning only within its correct protocol and transport context.

## 5. Protocol Architecture

Implement the proprietary layer as isolated components so standard OBD-II remains stable:

```text
Application scheduler
    |
    +-- SAE J1979 poller
    |
    +-- Nissan profile manager
            |
            +-- ECU identity matcher
            +-- read-only service allow list
            +-- signal definition table
            +-- response validator
            +-- unit/scaling decoder
    |
ISO-TP transport
    |
TWAI/CAN driver
```

Recommended source layout:

```text
main/
  obd2_source.c
  obd2_pid.c
  isotp_transport.c
  diagnostic_session.c
  nissan_profile.c
  nissan_signal_decoder.c
  diagnostic_policy.c
profiles/
  nissan_t32_<verified-ecu-family>.json
```

Profile data should include:

- ECU address and addressing mode
- Verified ECU identity match
- Request service and identifier
- Expected response service
- Minimum and maximum response length
- Byte offset, length, byte order, signedness, scale, offset, and unit
- Valid range and invalid/sentinel values
- Polling period, timeout, retries, and priority
- Source reference and validation status

## 6. Evidence-Driven Signal Development

Use one or more authorized evidence sources:

1. Nissan Electronic Service Manual information applicable to the exact VIN/market.
2. CONSULT-III Plus Data Monitor exports recorded from the same vehicle.
3. A synchronized CAN capture made during controlled operation, paired with CONSULT values.
4. A licensed diagnostic database or interface with documented redistribution rights.

Do not copy proprietary manuals, database contents, security algorithms, or customer VINs into a public repository.

### 6.1 Correlation procedure

For each candidate signal:

1. Record ECU identity and firmware/calibration.
2. Select one observable operating condition at a time.
3. Record the CONSULT value with a synchronized timestamp.
4. Capture the corresponding diagnostic response.
5. Repeat over at least five distinct values across the operating range.
6. Determine byte order, signedness, scale, and offset.
7. Validate on a separate drive and compare against CONSULT.
8. Mark the signal `verified` only after the error is within its acceptance limit.

Required evidence record:

| Field | Example |
|---|---|
| Signal | CVT fluid temperature |
| ECU identity | Redacted public family reference |
| Request/response | Stored privately |
| Formula | Documented only after verification |
| Unit | °C |
| Samples | Minimum 5 correlation points plus validation drive |
| Error limit | Engineering-defined, e.g. ±2 °C |
| Status | Candidate / Correlated / Verified / Rejected |

## 7. Polling and Traffic Management

Diagnostic traffic must remain a small fraction of available bus capacity and must never delay safety-critical vehicle messages.

Recommended initial schedule:

| Class | Typical period | Examples |
|---|---:|---|
| Fast | 500–1000 ms | RPM, vehicle speed, selected CVT speed/ratio |
| Medium | 2–5 s | Temperatures, voltage, pressure-related monitor values |
| Slow | 10–60 s | ECU identity, supported-signal discovery |
| Event | On state change | DTC-set change, online/offline state |

Controls:

- One outstanding diagnostic transaction per ECU.
- Token-bucket rate limiter per bus and per ECU.
- Exponential backoff after timeout, negative response, or bus error.
- Stop proprietary polling after repeated transport failures.
- Suspend nonessential polling during low voltage or unstable ignition.
- Cache slow data; do not repeatedly request static identifiers.
- Apply deadband only after acquiring a valid sample.
- Preserve timestamps for acquisition, gateway receipt, and cloud receipt.

Start conservatively at no more than 5–10 proprietary requests per second in total, then validate actual bus utilization. This is an engineering starting point, not a universal Nissan limit.

## 8. Data Quality Contract

Every decoded value must carry quality metadata:

```json
{
  "name": "cvt_fluid_temperature_c",
  "value": 74.0,
  "unit": "degC",
  "quality": "GOOD",
  "source": "nissan_consult_profile",
  "sample_time_ms": 1780000000000,
  "profile_version": "t32-verified-001"
}
```

Supported quality states:

- `GOOD`: verified response and valid range
- `STALE`: no fresh sample within the signal timeout
- `NOT_SUPPORTED`: verified ECU does not provide the signal
- `INVALID`: malformed, sentinel, or out-of-range response
- `UNVERIFIED`: decoder exists but has not passed vehicle validation
- `OFFLINE`: ECU or OBD client is unavailable

The cloud and dashboard must not convert missing, invalid, or unsupported data into `0`.

## 10. Dashboard Requirements

The Vehicle Health dashboard should separate portable SAE values from manufacturer-specific values:

- Clearly label Nissan-specific data.
- Show profile version and ECU identity-match status.
- Display `Not supported`, `Unverified`, and `Stale` explicitly.
- Provide per-module connection and freshness indicators.
- Show timestamps and data age.
- Present DTCs as read-only findings with module and status.
- Never claim that a missing proprietary value means the subsystem is healthy.
- Keep safety notices and read-only status visible.

Suggested pages:

1. **Driver health:** validated high-level engine, CVT, battery, and DTC status.
2. **Live trends:** selected standard and verified Nissan-specific trends.
3. **Workshop diagnostics:** module identities, read-only DTCs, quality, and evidence status.
4. **Maintenance:** threshold/rule observations with transparent reasoning.
5. **Engineering:** transport errors, profile match, request latency, retries, bus-load estimate, and raw-data references available only to authorized users.

## 11. Validation Plan

### Phase A — Bench and simulator

- Unit-test ISO-TP segmentation, flow control, timeout, and malformed-frame handling.
- Verify the service allow list rejects every write/control service.
- Replay sanitized captures; no vehicle connection required.
- Fuzz response lengths and invalid values.

### Phase B — Stationary vehicle

- Use fused power and approved OBD hardware.
- Confirm ignition voltage and CAN bitrate before polling.
- Read ECU identities.
- Run only documented read requests.
- Compare results with CONSULT or a recognized scan tool.
- Test ignition-off, sleep, wake, disconnect, and reconnect behavior.

### Phase C — Controlled road validation

- Use a second person to operate the logging equipment.
- Begin with standard OBD-II plus one proprietary module.
- Monitor CAN errors, ECU negative responses, ESP32 heap, TCP ACK rate, MQTT queue depth, LTE status, and dashboard freshness.
- Stop immediately if warning lamps, drivability changes, bus errors, or abnormal battery draw occur.

### Phase D — Soak test

- Minimum 2-hour controlled drive before a 24-hour mixed ignition-cycle test.
- Zero vehicle-control messages.
- Zero unauthorized diagnostic services.
- Zero gateway crashes.
- No sustained MQTT queue growth.
- No false conversion of unsupported/stale values to zero.
- Recovery after every planned ignition and network interruption.

## 12. Acceptance Criteria

| Area | Acceptance target |
|---|---|
| Safety policy | 100% prohibited-service rejection in tests |
| ECU profile | Exact identity match required before decode |
| Signal accuracy | Per-signal documented error threshold |
| Availability | ≥99.9% application availability during planned powered test |
| Recovery | Automatic after Wi-Fi, TCP, MQTT, LTE, and ignition interruption |
| Data quality | No unsupported or stale value represented as valid zero |
| Memory | No decreasing free-heap trend across soak test |
| Cloud | Bounded queue with visible drop/retry counters |

## 13. Implementation Phases

1. **Identity and safety foundation:** ISO-TP, policy firewall, ECU identity, counters, and logs.
2. **ECM pilot:** one or two well-evidenced read-only signals.
3. **CVT pilot:** CVT temperature first, then additional verified monitor values.
4. **ABS/VDC:** wheel-speed monitoring only after stationary validation.
5. **SRS and BCM:** identification and read-only DTC/status only.
6. **Cloud and HMI:** per-module topics, data-quality fields, and dashboard panels.
7. **Commercial hardening:** signed profiles, OTA rollback, tenant isolation, audit logs, privacy controls, and formal vehicle-compatibility matrix.

## 15. Commercialization Notes

A commercial product needs more than decoded PIDs:

- A tested vehicle/ECU compatibility matrix
- Signed firmware and signed decoder profiles
- Secure provisioning and per-device credentials
- Customer consent, privacy retention, and deletion controls
- Clear distinction between observation, estimation, and confirmed diagnosis
- Product-liability review and regional regulatory review
- Battery-drain limits and reliable ignition/sleep behavior
- Support tooling that can identify firmware, hardware, profile, and data-quality state remotely

Do not market an inferred value as manufacturer-authoritative. Display calculated trip, fuel, or maintenance estimates as estimates with their input quality and confidence.
